# Git workflow

Follow higher-priority instructions, user requests, repository conventions, and runtime permissions. Only the master agent manages branches and commits. Before feature implementation, inspect the current branch, relevant local and remote branch names, and staged and unstaged changes. If already on the appropriate feature branch, continue there. If a suitable existing branch is clearly identified, use it only when switching preserves the user's work and is permitted. If none exists, create a branch from the appropriate current base when permitted. Do not switch, stash, reset, overwrite, or move unrelated work to make a branch; if the right branch or safe base is unclear, continue independent work and ask before the dependent change.

Use meaningful lowercase kebab-case branch names under `feature/`, `fix/`, `chore/`, `test/`, or `refactor/` for the work type, unless a higher-priority instruction or repository convention specifies another format. For example, `feature/activation-metrics`. This default authorizes branch preparation for feature work only; follow the applicable authorization for other branch changes.

Stage and commit only at the user's request. Inspect the full staged and unstaged diff and keep unrelated changes out of the commit unless explicitly included by the user. Do not disturb pre-existing staged changes; if their intended inclusion is unclear, ask. Group related changes into cohesive commits when natural boundaries exist; keep dependent code and its tests together when that produces a useful, valid commit. Avoid splitting for its own sake. Use conventional commit subjects such as `feat(metrics): count successful activations`, `fix(metrics): preserve counter on restart`, `chore: update tooling`, `test: cover activation failure`, or `refactor: simplify metric collection`. The conventional commit type for a `feature/` branch is `feat`. Prefer a useful scope when it adds meaning. Respect project conventions and report created branches and commits.
